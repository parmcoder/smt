# SMT v0.1.0 Production Plan

## Summary

This milestone prioritizes the module and starter restructure. It does not
implement `smt extend`; extension execution follows as a later milestone.
Beads is the delivery status source of truth. This document is a milestone
sequence, not a second task tracker.

The accepted `.5` version-1 metadata slice includes the code-owned static
schema-v1 catalog with exactly 11 declarations and exact repository module
annotations. Five declarations are selectable (`web`, `mobile`, `api`,
`database`, `e2e`); six are non-selectable platform declarations (`container`,
`cicd`, `observability`, `iac`, `k8s`, `argocd`). Runnable starters, platform
repositories/scaffolds/runtime artifacts, and extension execution remain later
work.

The accepted `.3.1` runtime contract is implemented: generated roots contain
deterministic `compose.yaml` and `.env.example` and, for identity selection,
`traefik/dynamic.yaml`; root `.gitignore` ignores
`.env`, and offline rendering defines service selection, ports, project naming,
health/readiness, dependencies, and actionable future preflight errors. It does
not execute Podman or Compose or generate component Containerfiles.

The accepted `.3.3.1` API manifest contract is implemented: API-selected child
repositories receive deterministic `go.mod` and `go.sum` files for
`example.com/smt/apis` on Go 1.26.5, with selection-correct Huma, pgx,
golang-migrate, and pinned Go tools. The accepted `.3.3.2` API runtime contract
is implemented as deterministic API source, runtime defaults, and OpenAPI
assets; selected API Apply now runs `asdf exec go mod download` in staging
before child publication. The selected Web `.3.2.1` initializer is followed by
staged `asdf exec pnpm install`; Mobile similarly runs staged `flutter pub get`.
E2E package/browser/device setup and durable suites remain later explicit
milestones.

The accepted Web `.3.2.1` initializer is implemented: selected Web Apply
stages the root-pinned Next.js `16.2.9` CLI on Node.js `24.18.0`, preserves its
CLI-owned baseline and merged ignores, then runs `asdf exec pnpm install` before
publication. The pinned `npx` initializer and dependency setup may access the
npm registry; the later Web worker `.3.2.2/.3` lanes own quality, browser, and
runtime verification. Web Apply remains atomic.

See [[../specs/2026-08-17-smt-extensible-modules-design|SMT Extensible Modules Design]] and the canonical [[../../00-project/SMT - Implementation Spec|implementation specification]].

## Beads delivery map

The P0 restructure epic is `smt-4xf`, due 2026-08-23; its child issues are
the source of truth for delivery status. The deferred `smt extend` feature is
`smt-aah`, priority P3, due after 2026-08-24, and is blocked by the v0.1.0
release child. This map records ownership and sequencing only; it does not
duplicate Beads status.

The completed planning/decomposition task is `smt-4xf.11`. Its child ranges
are Web `.3.2.1-.3`, API `.3.3.1-.4`, Database `.3.4.1-.3`, Mobile
`.3.5.1-.3`, and verification-interface children `.6.1.1-.4`. Beads remains the live source of truth
for their status and sequencing.

## Approved mobile-first roadmap

The next P0 starter lane is Mobile rollup `smt-4xf.3.5` and children
`.3.5.1-.3`. Web rollup `smt-4xf.3.2` and children `.3.2.1-.3` are P2 and
remain P2; this roadmap does not alter their existing dependency edges.
Web `.3.2.1` is implemented as the CLI initializer below; `.3.2.2/.3` remain
deferred.

After staging the root `.tool-versions` pins `nodejs 24.18.0` and `pnpm 11.24.0`, Web Apply runs
this exact argument-array command in a temporary child and publishes it only
after success:

```sh
asdf exec npx --yes create-next-app@16.2.9 <staged-web-directory> --typescript --eslint --app --empty --tailwind --use-pnpm --skip-install --disable-git --agents-md --import-alias=@/*
```

The CLI-owned files are preserved and its `.gitignore` is merged. Apply then
run `asdf exec pnpm install` in the staged child. If pnpm blocks dependency build
scripts, Apply runs `asdf exec pnpm approve-builds --all` and retries. A failure retains CLI output
or setup output and reports
`asdf install nodejs 24.18.0`, `asdf current nodejs`, and the pinned CLI
`--help` path without publishing a partial destination. Web selection also
generates `web_worker` routing and skill metadata. After Apply, the local
workflow can run `asdf exec pnpm run dev` from `web-app/`; no real Web browser
or runtime lane is claimed until the later `.3.2.2/.3` work.

Mobile starts independently from the current `main` branch. It does not wait
for an API PR and does not require Web, API, or Database. Keep Mobile
backend-independent initially; typed API integration follows after the
generated API/Database runtime work is available.

Routing is `work_manager -> web_worker -> doc_writer` for Web and
`work_manager -> mobile_worker -> doc_writer` for Mobile, while the existing
`work_manager -> backend_worker -> doc_writer` route remains unchanged.
`mobile_worker` owns only assigned Flutter/Dart production code and focused
tests, does not delegate, and reports unavailable SDK, device, Android, or iOS
lanes explicitly.

- **`.3.5.1` manifest/analysis (implemented)** — Flutter owns the Mobile
  `pubspec.yaml`, `analysis_options.yaml`, and project baseline for Flutter
  `>=3.44.9` and Dart `>=3.12.0 <4.0.0`. The `pubspec.lock` and pinned
  `flutter_lints 6.0.0` policy are produced during Apply by
  `asdf exec flutter pub get` after the CLI's `--no-pub` step. The generated root pins
  `flutter 3.44.9-stable`; SDK tools, skills, MCP, signing, and host
  prerequisites remain outside app dependencies. The README guides
  `asdf install flutter 3.44.9-stable` and `asdf current flutter` before local
  analysis, tests, or device execution.
- **`.3.5.2` runnable MVP (implemented)** — Mobile-selected Apply now emits
  a staged Flutter CLI project. After staging root `.tool-versions`, Apply
  runs and preserves this exact command/output:

  ```sh
  asdf exec flutter --suppress-analytics create --empty --no-pub --platforms=android,ios --org=com.example.smt --project-name=smt_mobile --description="A provider-neutral SMT Flutter mobile starter." <staged-mobile-directory>
  ```

  There are no static Android/iOS templates. The Mobile worker adds the stable
  app/config/unit/widget/native-integration contract after CLI initialization;
  `--no-pub` keeps CLI creation offline; Apply then runs `asdf exec flutter pub
  get` after the generated Mobile files are complete. If the
  pinned toolchain is unavailable, Apply reports
  `asdf install flutter 3.44.9-stable` and `asdf current flutter` guidance and
  fails atomically before destination publication. Current evidence is asdf
  Flutter create, pub get, and analyze passing; Android SDK absence, incomplete
  Xcode, and missing CocoaPods leave device/build lanes unverified. Mobile
  remains backend-independent and outside OCI Compose.
- **`.3.5.3` verification (implemented)** — the generated Mobile contract
  includes `dart format`, `flutter analyze`, unit/widget tests, native
  `integration_test`, Android debug builds, and iOS debug builds with
  `--no-codesign` where supported. The opted-in lane passes format, analyze,
  and unit/widget tests; this host has no Android SDK or supported Android/iOS
  target, so integration and debug-build lanes are explicitly unverified.
- **`.6.1.3` Mobile native verification interface** — use `asdf exec dart
  format` plus direct `asdf exec flutter` analyze, test, integration, Android
  debug, and iOS debug lanes; do not generate a Mobile Taskfile. Lefthook
  invokes only the fast format/analyze lane on pre-push.

`.3.5.1`, `.3.5.2`, and `.3.5.3` are implemented; unavailable Mobile device
and debug-build lanes remain explicit host gaps. Web `.3.2.1` is the
implemented CLI baseline, while `.3.2.2/.3` remain deferred at P2.

## Milestones

1. **Design and contract (P0, `.5` metadata slice)** — record the five-layer
   model, decide the starter boundary, remove ambiguity around DevOps versus
   platform capabilities, and implement the schema-v1 static module catalog,
   exact 11 declarations, placement matrix, stable completion IDs, and
   catalog/config validation boundary. No `smt extend` implementation.
2. **Version-1 starter restructure** — `.3.1` locks the root runtime contract
   around Web, API, Database, and Mobile's non-OCI boundary. Web `.3.2.1`
   implements the staged CLI-owned Next.js baseline; the later `.3.2.2/.3`
   Web worker lanes remain deferred for quality, browser, and
   runtime work. The next P0 work is the independent Mobile `.3.5` lane
   described above; the broader `.3.2-.3.6` plan removes the DevOps
   prompt/stack and combined `infra` repository, then adds the later runnable
   Web, API, and PostgreSQL starter work plus Mobile verification.
3. **Safety and generated-workspace verification** — test selection and
   validation, deterministic atomic Apply with selected dependency setup, exact module annotations, the
   `.3.1` Compose/env contract, and the absence of secrets or fake domain
   behavior. Health/readiness endpoints, non-root runtimes, migrations, smoke
commands, remaining Web runtime assets, Database/API lifecycle verification,
and Mobile packaging remain component work. Apply performs the `.3.5.1`
   lockfile/dependency setup after `pub get`; `.3.5.2` owns the Flutter CLI project and `.3.5.3`
   owns its stable app/test contract and verification evidence.
   Catalog verification declarations and runtime preflight are not executed by
   `smt apply`.
4. **API manifest contract (`.3.3.1`, implemented)** — emit API-only and
   API+Database static `go.mod`/`go.sum` variants with exact runtime and tool
   pins, direct checksums, no API manifests when API is absent, and no download
   or installation during apply. Source-closure checks remain later evidence.
5. **API runtime and OpenAPI contract (`.3.3.2`, implemented)** — emit API
   source, typed `env/v11` configuration, the generated API child Taskfile,
   runtime defaults, health/readiness/metrics/request-ID/recovery/shutdown
   behavior, shared Huma OpenAPI assets, and offline regeneration output only
   when API is selected. No database code, credentials, domain CRUD,
   Containerfile, root Taskfile, packaging, or runtime execution is added. The
   API+Database child gets the same API Taskfile but no database
   migration/readiness tasks yet; root/database aggregation is `.6.1.2` and
   later. Defer durable unit/race/fuzz/integration suites to `.3.3.3` and
   non-root packaging/runtime verification to `.3.3.4`.
6. **Production candidate** — run repository quality gates and a disposable
   real-workspace review with Podman Compose. Record evidence and unresolved
   risks in the owning Beads issues; do not call the milestone complete from
   this document alone.
7. **Later: `smt extend`** — implement catalog resolution, dependency and path
   checks, dry-run/confirmation, Git-safe repository creation, and idempotent
   module extension only after the runtime/starter work is accepted.
8. **Later discovery** — evaluate AWS + Apptainer + OpenTofu as a concrete
   runtime/platform combination before adding implementation commitments.

## Release gates

The production tag requires accepted Beads work, clean repository state,
focused tests, `go test ./...`, `go vet ./...`, documentation consistency,
`git diff --check`, and human verification of the generated workspace and
later Podman runtime. The `.5` checks cover catalog schema, exact declarations,
placement, completion IDs, references, paths, capabilities, dependency cycles,
and early rejection of non-selectable platform metadata. The `.3.1` checks
cover deterministic Compose/env output, selection filtering, canonical ports,
project naming, health/dependency declarations, empty credentials, and
actionable preflight errors. The `.3.3.2` checks cover API-only selection,
deterministic API source and `.env.example` assets, API-only absence of
pgx/migrate/database code, exact runtime defaults, health/readiness/metrics,
request IDs, recovery/shutdown assets, offline Huma OpenAPI generation, and
byte-identical regeneration across fresh Apply destinations. The `.3.5.3`
checks cover Dart formatting, Flutter analysis, unit/widget and integration
tests, Android/iOS debug builds, and explicit unavailable-lane reporting. A
failed safety or runtime gate blocks release.
The release must not imply that `smt extend`, Kubernetes, ArgoCD, AWS,
Apptainer, or OpenTofu execution is available.

## Assumptions and risks

- Version 1 has no external users, so the planned rewrite does not require a
  compatibility migration.
- The five layers stay in one repository until ownership and deployment
  boundaries justify extraction.
- The static schema-v1 module catalog and repository `modules: [id...]`
  annotations are implemented metadata. The catalog contains exactly 11
  declarations: selectable `web`, `mobile`, `api`, `database`, and `e2e`; plus
  non-selectable `container`, `cicd`, `observability`, `iac`, `k8s`, and
  `argocd`. Placement modes are `attached`, `shared`, and `independent`; the
  built-in matrix is independent self-targets for Web/Mobile/API/Database,
  attached `repo` for E2E, attached Web+API for container, attached
  repo+Web+Mobile+API+Database for CI/CD, attached Web+API+Database for
  observability, and independent `platform/iac`, `platform/k8s`, and
  `platform/argocd` for IaC/Kubernetes/ArgoCD. ArgoCD requires `k8s`.
- Stable completion criteria are `web.declaration`, `mobile.declaration`,
  `api.declaration`, `database.declaration`, `e2e.declaration`,
  `container.declaration`, `cicd.repository-boundary`,
  `observability.boundary`, `iac.provider-neutral`, `k8s.static-validation`,
  and `argocd.sync-policy`. Catalog/config validation covers schema,
  duplicate/unknown references, safe paths, capabilities, and dependency
  cycles. `Config.LoadBytes` accepts valid known platform metadata, while
  `Apply` and `ValidateBlueprint` reject non-selectable platform metadata
  before topology or staging/destination mutation.
- `smt new` offers a default-no E2E quality-root declaration after the existing
  component prompts. Opting in records `modules: [e2e]` on the root; current
  Apply remains metadata-only, while the P0 `smt-4xf.14` rollup will generate
  separate attached `e2e/web` and `e2e/mobile` packages only for selected Web
  or Mobile targets. No-target E2E remains valid metadata-only. Web uses
  Playwright and Mobile uses Flutter's native `integration_test`; the first
  lane is contract smoke with stable hooks, Web `/healthz`, optional API
  reachability, and Mobile `mobile-home`/`api-status`. Local tasks delegate
  startup to existing component commands and report missing tools/devices;
  Apply does not install E2E packages, browsers, SDKs, credentials, or remote CI;
  selected project dependencies are prepared before publication.
- The `.5` slice adds declarations and validation only: no platform
  repositories/scaffolds/runtime artifacts, no tool/skill/MCP installation, no
  host configuration mutation, and no Compose/Podman/Kubernetes/ArgoCD/OpenTofu
  runtime. Runnable starters and `smt extend` remain deferred.
- `.3.1` adds only contract-level root files: deterministic `compose.yaml`,
  `.env.example`, conditional identity `traefik/dynamic.yaml`, and root
  `.gitignore` handling for `.env`. Compose emits only
  selected `web`, `api`, and `database` services; Mobile remains outside OCI.
  Defaults are `3000:3000`, `8080:8080`, and `5432:5432`, overridden by
  `WEB_PORT`, `API_PORT`, and `DATABASE_PORT`. Project names use the safe
  lowercase-hyphen destination basename, capped at 63 characters, with
  `smt-workspace` fallback. Web/API/Database health and dependency contracts
  are declarative; no credentials or `.env` are generated. OCI-selected roots
  also receive explicit root Compose Taskfile entrypoints that pass `.env` to
  Podman Compose, while Apply still does not invoke Podman, Compose, socket
  probing, or runtime health checks.
- The pure runtime preflight API is reserved for later Taskfile/CLI consumers.
  It reports invalid, colliding, or occupied ports and missing Podman or
  Podman Compose prerequisites through actionable injected checks; `smt apply`
  does not invoke it.
- `.3.3.1` emits API `go.mod`/`go.sum` only when API is selected. The module is
  `example.com/smt/apis` with `go 1.26.5`; Huma v2.39.1 is API-only and pgx
  v5.10.0 plus golang-migrate v4.19.1 are API+Database-only. Go tool
  directives pin govulncheck/x/vuln v1.7.0, golangci-lint v2.12.2, and migrate
  only for API+Database. API-only excludes pgx/migrate; no API emits no
  manifests. Direct sums are present; full transitive closure and source
  verification remain outside the manifest contract.
- Apply writes these static manifests without invoking `go`, `go mod`, a
  package manager, the network, or tool installation. SDK/editor/agent tools
  are not module dependencies. `go mod tidy` remains a later source-closure
  check; the generated child `mod` task exercises `go mod verify` for the
  emitted manifest.
- `.3.3.2` emits API-selected `main.go`, `internal/server/server.go`,
  `cmd/openapi/main.go`, `.env.example`, and `openapi.yaml` alongside the
  manifests. No API selection emits no API child or API assets. The module
  remains `example.com/smt/apis` on Go 1.26.5, using Huma v2.39.1 through Gin
  (Gin v1.12.0) and Prometheus `github.com/prometheus/client_golang v1.24.1`. Runtime defaults are
  `HTTP_ADDR=:8080`, `APP_ENV=development`, `LOG_LEVEL=info`,
  `HTTP_READ_TIMEOUT=15s`, `HTTP_READ_HEADER_TIMEOUT=5s`,
  `HTTP_WRITE_TIMEOUT=15s`, `HTTP_IDLE_TIMEOUT=60s`,
  `HTTP_MAX_HEADER_BYTES=1048576`, and `HTTP_SHUTDOWN_TIMEOUT=10s`.
  API-only source has no pgx/migrate/database code; API+Database retains
  pgx/migrate manifest dependencies only. Runtime defaults, Huma OpenAPI 3.1
  metadata title `SMT API`, version `v0.1.0`, and `/docs`, `/openapi.json`,
  `/openapi.yaml`, `/healthz`, `/readyz`, and `/metrics` routes, health/readiness,
  same-listener metrics, safe `X-Request-ID` values,
  JSON slog panic recovery, and `SIGINT`/`SIGTERM` timed signal shutdown are implemented. The
  offline `cmd/openapi` command regenerates the shared Huma YAML, and the
  committed artifact is byte-identical across fresh Apply destinations.
- The generated API server `Config` carries direct typed
  `github.com/caarlos0/env/v11 v11.4.1` `env`/`envDefault` tags, including
  `slog.Level` and `time.Duration` fields. `LoadConfig()` calls plain
  `env.Parse(&cfg)`, so native caarlos/TextUnmarshaler parsing controls
  malformed-value errors; no separate semantic conversion or post-parse
  validation is added. `Run` logs a structured `configuration load
  failed` event and panics with the native parse error before constructing the
  application; normal Gin/Huma runtime and graceful shutdown remain unchanged.
  The exact pin/checksums are in both static API manifest variants. API selection emits a child `Taskfile.yml` with
  `dotenv: ['.env']`, `build`, `run`, `test`, `coverage`, `mod`, `openapi`, and
  `verify` tasks; it does not copy or mutate `.env`. Task v3.52.0 verified the
  dotenv-driven `/healthz` harness and bounded process cleanup. `smt apply`
  writes this child Taskfile but does not run Task, install implicitly, access
  the network, or change the root Taskfile. API-selected Apply and its API+Database
  variant have no database
  migration/readiness tasks yet; those and root aggregation belong to
  `smt-4xf.6.1.2` and later.
- API-selected Apply writes embedded API assets, then runs `asdf exec go mod
  download` in the staged child before publication. It does not install tools,
  execute Task, invoke Podman, start listeners, or run runtime verification. No credentials,
  domain CRUD, DB connectivity/readiness, migrations, root Taskfile changes,
  Containerfiles, or non-root packaging are generated. Durable unit/race/fuzz/integration
  suites remain `.3.3.3`; non-root packaging/runtime verification remains
  `.3.3.4`; human and Podman gates remain later evidence.
- The accepted taxonomy change means new version-1 blueprints no longer
  generate DevOps-shaped output, and `smt apply` rejects legacy DevOps-shaped
  configurations before mutation. Runnable starter/runtime assets remain
  planned and must not be inferred as delivered here.
- Generated blueprints carry only the exact `smt`/`v0.1.0`/`v1` provenance
  contract documented in the implementation specification. Missing,
  unsupported, or unknown provenance fails before mutation; provenance-free
non-generated version-1 configurations remain usable for lifecycle and
diagnostics but are not applyable as new generated blueprints. Blueprint and
static generation remains byte-stable without network access for identical
selections in fresh destinations. Selected Web `.3.2.1` Apply may access the
npm registry for its pinned `npx` initializer and staged `pnpm install`; Mobile
and API Apply may access their dependency registries for staged setup. E2E
packages, browsers, devices, services, and host tooling remain explicit, and
existing destinations are refused without overwrite, merge, regeneration,
upgrade, or `smt extend` execution.
- The reviewed runtime baseline is fixed for this milestone: Go 1.26.5, pgx
  v5.10.0, Next.js 16.2.9 on Node 24.18.0, Flutter >=3.44.9, PostgreSQL 18,
  and Podman 5.8.3+ with a Compose provider. The accepted `.3.2.1` Web
  CLI-owned baseline, `.3.3.2` Go API source/OpenAPI assets, Mobile `.3.5.1`
  manifests, `.3.5.2` source/platform assets, and `.3.5.3` app/test
  verification contract are implemented. Web `.3.2.2/.3` dependency, quality,
browser, and runtime lanes, Mobile device/integration/debug-build lanes,
Web Containerfiles, Database/API lifecycle verification, packaging, and later
runtime gates remain deferred or explicitly unverified. Database `.3.4.1`
runtime/readiness assets are implemented; API-owned migration work remains
`.3.4.2`.
